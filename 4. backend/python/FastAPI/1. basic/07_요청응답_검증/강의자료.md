# 7교시 — 요청·응답 데이터 검증

## 학습 목표

- FastAPI의 자동 검증 흐름을 이해하고 422 응답을 해석할 수 있다
- HTTPException으로 명시적인 오류 응답을 반환할 수 있다
- 커스텀 예외 핸들러로 에러 응답 형식을 통일할 수 있다
- 비즈니스 로직 검증 패턴을 API 계층에서 올바르게 구현할 수 있다

## 이번 교시의 범위

7교시는 **FastAPI 요청/응답 흐름에서 검증이 어떻게 작동하는지**를 보는 시간입니다.  
Pydantic 모델 작성법 자체보다, 요청 파싱, 422 응답 해석, `HTTPException`, 커스텀 예외 핸들러, 비즈니스 로직 검증의 위치에 집중합니다.

필드 타입, `Field()` 제약, `field_validator`, `model_validator` 같은 모델링 문법은 6교시에서 이미 학습한 내용을 활용합니다.

---

## 1. FastAPI의 자동 검증 흐름

```
클라이언트 요청
     │
     ▼
FastAPI 라우터 매칭
     │
     ▼
Pydantic 모델 파싱 & 검증 ──실패──► 422 Unprocessable Entity
     │ 성공
     ▼
엔드포인트 함수 실행
     │
     ▼
응답 직렬화 (response_model 지정 시 출력 검증)
     │
     ▼
HTTP 응답 반환
```

FastAPI는 요청이 들어오는 순간 Pydantic을 통해 자동으로 타입 변환과 검증을 수행합니다.  
개발자가 별도 검증 코드를 작성하지 않아도 **타입 오류는 422**로 자동 처리됩니다.

---

## 2. 422 Unprocessable Entity

Pydantic 검증 실패 시 FastAPI가 자동으로 반환하는 응답입니다.

### 요청 예시

```json
POST /users
{
    "username": "a",
    "email": "not-an-email",
    "age": -5
}
```

### 422 응답 구조

```json
{
    "detail": [
        {
            "type": "string_too_short",
            "loc": ["body", "username"],
            "msg": "String should have at least 3 characters",
            "input": "a",
            "ctx": {"min_length": 3}
        },
        {
            "type": "value_error",
            "loc": ["body", "age"],
            "msg": "Value error, 나이는 0~150 사이여야 합니다.",
            "input": -5
        }
    ]
}
```

`loc` 배열이 오류 위치를 나타냅니다: `["body", "필드명"]`, `["path", "파라미터명"]`, `["query", "파라미터명"]`

## 3. HTTPException — 명시적 오류 반환

Pydantic 검증 이후의 **비즈니스 로직 오류**는 `HTTPException`으로 처리합니다.

```python
from fastapi import FastAPI, HTTPException

app = FastAPI()

fake_users_db = {1: {"id": 1, "name": "홍길동", "active": True}}

@app.get("/users/{user_id}")
def get_user(user_id: int):
    user = fake_users_db.get(user_id)

    if user is None:
        raise HTTPException(status_code=404, detail="사용자를 찾을 수 없습니다.")

    if not user["active"]:
        raise HTTPException(status_code=403, detail="비활성화된 계정입니다.")

    return user
```

### 상황별 상태 코드 가이드

| 상황 | 상태 코드 | 설명 |
|------|----------|------|
| 리소스 없음 | 404 Not Found | ID로 조회했으나 존재하지 않음 |
| 권한 없음 | 403 Forbidden | 접근 권한 부족 |
| 인증 필요 | 401 Unauthorized | 로그인 필요 |
| 잘못된 요청 | 400 Bad Request | 비즈니스 규칙 위반 |
| 충돌 | 409 Conflict | 이미 존재하는 리소스 |
| 서버 오류 | 500 Internal Server Error | 예상치 못한 서버 오류 |

## 4. detail 구조화

`detail`에 문자열 대신 dict를 넣어 더 많은 정보를 담을 수 있습니다.

```python
raise HTTPException(
    status_code=400,
    detail={
        "code": "INSUFFICIENT_STOCK",
        "message": "재고가 부족합니다.",
        "available": 3,
        "requested": 10
    }
)
```

응답:
```json
{
    "detail": {
        "code": "INSUFFICIENT_STOCK",
        "message": "재고가 부족합니다.",
        "available": 3,
        "requested": 10
    }
}
```

## 5. 커스텀 예외 핸들러

팀 전체에서 통일된 에러 응답 형식을 사용하려면 예외 핸들러를 등록합니다.

```python
from fastapi import FastAPI, HTTPException, Request
from fastapi.responses import JSONResponse
from fastapi.exceptions import RequestValidationError

app = FastAPI()

# ── 공통 에러 응답 형식 ─────────────────────────────
def error_response(code: str, message: str, details=None):
    body = {"success": False, "error": {"code": code, "message": message}}
    if details:
        body["error"]["details"] = details
    return body

# ── 422 검증 오류 핸들러 ────────────────────────────
@app.exception_handler(RequestValidationError)
async def validation_exception_handler(request: Request, exc: RequestValidationError):
    errors = []
    for err in exc.errors():
        errors.append({
            "field": ".".join(str(loc) for loc in err["loc"][1:]),  # body 제거
            "message": err["msg"],
            "type": err["type"],
        })
    return JSONResponse(
        status_code=422,
        content=error_response("VALIDATION_ERROR", "입력값이 올바르지 않습니다.", errors),
    )

# ── HTTPException 핸들러 ────────────────────────────
@app.exception_handler(HTTPException)
async def http_exception_handler(request: Request, exc: HTTPException):
    return JSONResponse(
        status_code=exc.status_code,
        content=error_response("HTTP_ERROR", str(exc.detail)),
    )
```

### 커스텀 핸들러 적용 전/후 비교

**기본 422 응답:**
```json
{"detail": [{"type": "missing", "loc": ["body", "name"], "msg": "Field required"}]}
```

**커스텀 핸들러 422 응답:**
```json
{
    "success": false,
    "error": {
        "code": "VALIDATION_ERROR",
        "message": "입력값이 올바르지 않습니다.",
        "details": [{"field": "name", "message": "Field required", "type": "missing"}]
    }
}
```

## 6. 비즈니스 로직 검증 패턴

### 패턴 1 — 중복 체크

```python
@app.post("/users", status_code=201)
def create_user(user: UserCreate):
    # 이메일 중복 검사
    existing = next((u for u in users_db.values() if u["email"] == user.email), None)
    if existing:
        raise HTTPException(status_code=409, detail="이미 사용 중인 이메일입니다.")

    new_id = max(users_db.keys(), default=0) + 1
    users_db[new_id] = {"id": new_id, **user.model_dump()}
    return users_db[new_id]
```

### 패턴 2 — 상태 전이 검증

```python
ALLOWED_TRANSITIONS = {
    "pending": ["processing", "cancelled"],
    "processing": ["shipped", "cancelled"],
    "shipped": ["delivered"],
    "delivered": [],
    "cancelled": [],
}

@app.patch("/orders/{order_id}/status")
def update_order_status(order_id: int, new_status: str):
    order = orders_db.get(order_id)
    if not order:
        raise HTTPException(status_code=404, detail="주문을 찾을 수 없습니다.")

    current = order["status"]
    if new_status not in ALLOWED_TRANSITIONS[current]:
        raise HTTPException(
            status_code=400,
            detail=f"'{current}' 상태에서 '{new_status}'로 변경할 수 없습니다."
        )

    order["status"] = new_status
    return order
```

### 패턴 3 — 재고 검증

```python
@app.post("/orders")
def create_order(order: OrderCreate):
    total = 0
    for item in order.items:
        product = products_db.get(item.product_id)
        if not product:
            raise HTTPException(
                status_code=404,
                detail=f"상품 ID {item.product_id}를 찾을 수 없습니다."
            )
        if product["stock"] < item.quantity:
            raise HTTPException(
                status_code=400,
                detail={
                    "code": "INSUFFICIENT_STOCK",
                    "product_id": item.product_id,
                    "available": product["stock"],
                    "requested": item.quantity,
                }
            )
        total += product["price"] * item.quantity

    # 재고 차감
    for item in order.items:
        products_db[item.product_id]["stock"] -= item.quantity

    return {"order_total": total, "status": "pending"}
```

## 7. response_model — 응답 검증 & 필터링

```python
from fastapi import FastAPI
from pydantic import BaseModel

class UserCreate(BaseModel):
    username: str
    password: str

class UserResponse(BaseModel):
    id: int
    username: str
    # password 없음

@app.post("/users", response_model=UserResponse, status_code=201)
def create_user(user: UserCreate):
    new_user = {"id": 1, "username": user.username, "password": user.password}
    return new_user  # response_model이 password를 자동으로 제거
```

### response_model_exclude_unset

수정 API에서 변경되지 않은 필드는 응답에서 제외할 때 사용합니다.

```python
@app.patch("/users/{user_id}", response_model=UserResponse, response_model_exclude_unset=True)
```

## 8. 검증 레이어 구조 정리

```
입력 데이터
    │
    ▼
[Layer 1] Pydantic 타입 검증     ← Field(), validator
    │ 실패 → 422
    ▼
[Layer 2] FastAPI 경로 파라미터  ← Path(), Query()
    │ 실패 → 422
    ▼
[Layer 3] 비즈니스 로직 검증     ← HTTPException(400, 404, 409 ...)
    │ 실패 → 4xx
    ▼
[Layer 4] 응답 직렬화 & 필터링   ← response_model
    │
    ▼
클라이언트 응답
```

## 핵심 정리

| 상황 | 처리 방법 |
|------|----------|
| 타입 / 형식 오류 | Pydantic 자동 처리 → 422 |
| 리소스 없음 | `raise HTTPException(404)` |
| 비즈니스 규칙 위반 | `raise HTTPException(400)` |
| 중복 리소스 | `raise HTTPException(409)` |
| 응답 필드 제어 | `response_model=OutputSchema` |
| 에러 형식 통일 | `@app.exception_handler(...)` |
