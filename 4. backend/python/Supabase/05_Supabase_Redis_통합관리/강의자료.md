# 5교시: Supabase·Redis 통합 사용자 정보·대화 이력 관리

**소요시간:** 90분 (이론 30분 + 실습 60분)  
**사전 지식:** 3교시(Supabase Auth), 4교시(Redis 세션)

---

## 학습 목표

- Supabase Auth 로그인 결과를 Redis 앱 세션으로 변환한다
- `X-Session-Id` 기반으로 사용자 상태를 유지한다
- Supabase에는 영구 대화 이력을 저장하고 Redis에는 최근 대화 캐시를 저장한다
- 사용자별 프로필, 대화방, 메시지를 통합 API로 관리한다
- Redis 세션 만료와 Supabase 토큰 검증의 관계를 이해한다
- Redis 캐시가 삭제된 경우를 대비한 복구(rebuild) 전략을 구현한다

---

## 1. 최종 아키텍처

```
[Client]
   │
   │ 1. email/password 로그인
   ▼
[FastAPI] ──────────── Supabase Auth
   │                       │
   │ 2. 앱 세션 저장        │ access_token 검증
   ▼                       ▼
[Redis]             [Supabase PostgreSQL]
세션, 최근 대화 캐시    프로필, 대화방, 전체 메시지
```

Supabase와 Redis는 서로를 대체하지 않습니다. 역할이 다릅니다.

| 데이터 | 저장 위치 | 이유 |
|--------|-----------|------|
| 회원 계정 | Supabase Auth | 인증 전용 시스템 |
| 프로필 | Supabase PostgreSQL | 영구 보관, 관계형 조회 |
| 전체 대화 이력 | Supabase PostgreSQL | 나중에 다시 조회 가능 |
| 앱 세션 | Redis | 빠른 조회, TTL 자동 만료 |
| 최근 대화 캐시 | Redis | LLM 컨텍스트용 최근 N개 빠른 읽기 |

## 2. 로그인 흐름: Auth → 앱 세션

Supabase Auth 로그인은 access_token과 refresh_token을 반환합니다.  
FastAPI는 이 토큰을 Redis에 저장하고 자체 `session_id`를 발급합니다.

```python
@app.post("/auth/login")
def login(data: LoginRequest):
    # 1. Supabase Auth로 로그인
    result = public_client().auth.sign_in_with_password({
        "email": data.email,
        "password": data.password,
    })

    user_id      = str(result.user.id)
    email        = result.user.email
    access_token = result.session.access_token
    refresh_token = result.session.refresh_token

    # 2. Redis에 앱 세션 저장
    session_id = str(uuid4())
    key = f"app_session:{session_id}"
    r.hset(key, mapping={
        "user_id":       user_id,
        "email":         email,
        "access_token":  access_token,
        "refresh_token": refresh_token,
        "created_at":    now_ts(),
        "last_seen_at":  now_ts(),
    })
    r.expire(key, SESSION_TTL_SECONDS)

    return {"session_id": session_id}
```

이후 클라이언트는 `X-Session-Id`만 보냅니다. access_token은 서버 내부에서만 관리됩니다.

```http
X-Session-Id: 58f2a3d1-...
```

## 3. 요청마다 세션과 토큰 이중 검증

Redis 세션이 있다고 해서 무조건 신뢰하면 안 됩니다.  
세션 안에 저장된 Supabase access_token도 함께 검증합니다.

```python
def get_current_session(
    x_session_id: str | None = Header(default=None, alias="X-Session-Id"),
) -> AppSession:
    if not x_session_id:
        raise HTTPException(401, "X-Session-Id 헤더가 필요합니다")

    key = f"app_session:{x_session_id}"
    data = r.hgetall(key)

    # 1단계: Redis 세션 존재 여부 확인
    if not data:
        raise HTTPException(401, "세션이 없거나 만료되었습니다. 다시 로그인하세요.")

    # 2단계: Supabase access_token 유효성 검증
    try:
        auth_result = public_client().auth.get_user(data["access_token"])
    except Exception:
        r.delete(key)  # 유효하지 않은 세션 삭제
        raise HTTPException(401, "토큰이 만료되었습니다. 다시 로그인하세요.")

    # user_id 불일치 탐지 (변조 방지)
    if str(auth_result.user.id) != data["user_id"]:
        r.delete(key)
        raise HTTPException(401, "세션 사용자 정보가 일치하지 않습니다.")

    # 세션 TTL 갱신
    r.expire(key, SESSION_TTL_SECONDS)
    r.hset(key, "last_seen_at", now_ts())

    return AppSession(
        session_id=x_session_id,
        user_id=data["user_id"],
        email=data["email"],
    )
```

이 검증은 두 가지를 동시에 확인합니다.

| 확인 항목 | 실패 시 조치 |
|-----------|-------------|
| Redis 세션 존재 | 401 — 다시 로그인 안내 |
| Supabase access_token 유효 | 세션 삭제 + 401 |
| user_id 일치 | 세션 삭제 + 401 |

## 4. 메시지 저장: Supabase + Redis 이중 저장

메시지를 저장할 때 영구 보관과 캐시 두 곳에 나눠서 저장합니다.

```
메시지 저장 요청
        │
        ├── 1. Supabase에 영구 저장 (실패 시 Redis 저장 안 함)
        │          ↓
        └── 2. Redis에 최근 캐시 저장 (실패해도 괜찮음)
```

```python
@app.post("/conversations/{conversation_id}/messages", status_code=201)
def add_message(
    conversation_id: str,
    data: MessageCreate,
    session: AppSession = Depends(get_current_session),
):
    # 대화방 소유권 확인
    get_owned_conversation(conversation_id, session.user_id)

    # 1. Supabase에 영구 저장 (반드시 성공해야 함)
    result = (
        admin_client()
        .table("chat_messages")
        .insert({
            "conversation_id": conversation_id,
            "owner_id":        session.user_id,
            "role":            data.role,
            "content":         data.content,
        })
        .select("*")
        .execute()
    )
    message = one_or_404(result.data, "메시지 저장 실패")

    # 2. Redis에 최근 캐시 저장 (실패해도 원본은 Supabase에 있음)
    cache_key = f"recent_history:{session.user_id}:{conversation_id}"
    r.rpush(cache_key, json.dumps({
        "role":       data.role,
        "content":    data.content,
        "created_at": message["created_at"],
    }, ensure_ascii=False))
    r.ltrim(cache_key, -RECENT_HISTORY_LIMIT, -1)
    r.expire(cache_key, RECENT_HISTORY_TTL_SECONDS)

    return message
```

### 왜 Supabase를 먼저 저장하는가?

```
❌ Redis 먼저 저장 → Supabase 저장 실패
  Redis에는 있지만 Supabase에는 없는 메시지 발생
  서버 재시작 후 데이터 유실 — 복구 불가

✅ Supabase 먼저 저장 → Redis 저장 실패
  Supabase에 원본이 있으므로 /recent/rebuild로 복구 가능
```

## 5. 최근 메시지 캐시 vs 전체 메시지

두 가지 엔드포인트를 제공합니다.

```
GET /conversations/{id}/messages         — Supabase 전체 이력
GET /conversations/{id}/recent           — Redis 최근 N개 캐시
POST /conversations/{id}/recent/rebuild  — Supabase에서 캐시 복구
```

### 최근 캐시 조회

```python
@app.get("/conversations/{conversation_id}/recent")
def get_recent(
    conversation_id: str,
    session: AppSession = Depends(get_current_session),
):
    get_owned_conversation(conversation_id, session.user_id)

    cache_key = f"recent_history:{session.user_id}:{conversation_id}"
    raw = r.lrange(cache_key, 0, -1)
    return [json.loads(m) for m in raw]
```

### 캐시 복구 (rebuild)

Redis가 재시작되거나 TTL이 만료되면 캐시가 비어 있을 수 있습니다.  
Supabase의 영구 메시지에서 최근 N개를 읽어 Redis를 다시 채웁니다.

```python
@app.post("/conversations/{conversation_id}/recent/rebuild")
def rebuild_recent(
    conversation_id: str,
    session: AppSession = Depends(get_current_session),
):
    get_owned_conversation(conversation_id, session.user_id)

    # Supabase에서 최근 메시지 조회
    result = (
        admin_client()
        .table("chat_messages")
        .select("role, content, created_at")
        .eq("conversation_id", conversation_id)
        .order("created_at", desc=True)
        .limit(RECENT_HISTORY_LIMIT)
        .execute()
    )
    messages = list(reversed(result.data))  # 오래된 것부터 순서 복원

    # Redis 캐시 재생성
    cache_key = f"recent_history:{session.user_id}:{conversation_id}"
    r.delete(cache_key)  # 기존 캐시 삭제
    for msg in messages:
        r.rpush(cache_key, json.dumps(msg, ensure_ascii=False))
    r.expire(cache_key, RECENT_HISTORY_TTL_SECONDS)

    return {"rebuilt": len(messages)}
```

## 6. 접근 제어

통합 API에서도 사용자는 자신의 대화만 접근할 수 있어야 합니다.

```python
def get_owned_conversation(conversation_id: str, user_id: str) -> dict:
    result = (
        admin_client()
        .table("chat_conversations")
        .select("*")
        .eq("id", conversation_id)
        .eq("owner_id", user_id)  # 내 대화인지 확인
        .limit(1)
        .execute()
    )
    if not result.data:
        raise HTTPException(404, "대화방을 찾을 수 없습니다")
    return result.data[0]
```

`service_role` 키는 RLS를 우회하므로, 서버 코드의 소유자 필터가 필수입니다.

## 7. 이번 교시 API

```
GET   /health
POST  /auth/signup
POST  /auth/login
POST  /auth/logout
GET   /me
POST  /conversations
GET   /conversations
POST  /conversations/{conversation_id}/messages
GET   /conversations/{conversation_id}/messages
GET   /conversations/{conversation_id}/recent
POST  /conversations/{conversation_id}/recent/rebuild
```

### 실습 순서

1. Redis 서버 실행 확인
2. Supabase SQL Editor에서 `schema.sql` 실행
3. `POST /auth/signup` → 사용자 A, B 각각 가입
4. `POST /auth/login` 사용자 A → `session_id` 받기
5. Swagger에서 `X-Session-Id` 헤더 추가
6. `GET /me` → 프로필 확인
7. 대화방 생성 → 메시지 여러 개 저장
8. `GET /conversations/{id}/messages` (Supabase 전체)와 `GET /recent` (Redis 캐시) 비교
9. Redis 캐시 직접 삭제: `redis-cli DEL recent_history:{user_id}:{conversation_id}`
10. `GET /recent` → 빈 배열 확인
11. `POST /recent/rebuild` → 캐시 복구 확인
12. 사용자 B 로그인 → A의 대화 접근 시 404 확인

## 8. 장애 상황 대응

| 상황 | 발생 결과 | 대응 방법 |
|------|-----------|-----------|
| Redis 세션 만료 | `401` | 다시 로그인 |
| Supabase access_token 만료 | `401` | refresh_token으로 갱신 or 재로그인 |
| Redis 캐시 삭제 | `/recent` 빈 배열 반환 | `/recent/rebuild` 호출 |
| Supabase 저장 실패 | `500` | Redis도 저장하지 않음 |
| 서버 코드에서 owner 필터 누락 | 타인 데이터 노출 위험 | `get_owned_conversation` 공통 함수 사용 |

### access_token 갱신 (심화)

이번 예제는 갱신 구현까지는 다루지 않습니다. 실무에서는 아래처럼 처리합니다.

```python
# access_token 만료 시 Redis의 refresh_token으로 갱신
result = public_client().auth.refresh_session(refresh_token)
new_access_token = result.session.access_token

# Redis 세션 업데이트
r.hset(key, "access_token", new_access_token)
r.expire(key, SESSION_TTL_SECONDS)
```

## 9. 전체 과정 복습: 데이터 흐름 총정리

```
회원가입
  │ POST /auth/signup
  ├── Supabase Auth: auth.users 생성
  └── Supabase PostgreSQL: profiles 생성

로그인
  │ POST /auth/login
  ├── Supabase Auth: 이메일/비밀번호 검증 → access_token 발급
  └── Redis: app_session:{session_id} 저장 (access_token 포함)

대화방 생성
  │ POST /conversations (X-Session-Id 헤더)
  ├── Redis: 세션 확인 + Supabase 토큰 검증
  └── Supabase PostgreSQL: chat_conversations 저장

메시지 저장
  │ POST /conversations/{id}/messages
  ├── Redis: 세션 확인 + Supabase 토큰 검증
  ├── Supabase PostgreSQL: chat_messages 저장 (영구)
  └── Redis: recent_history:{user_id}:{conv_id} 캐시 저장

캐시 복구
  │ POST /conversations/{id}/recent/rebuild
  ├── Supabase PostgreSQL: 최근 N개 메시지 조회
  └── Redis: recent_history 재생성
```

## 10. 흔한 실수와 해결법

| 오류 | 원인 | 해결 |
|------|------|------|
| `401` on every request | `X-Session-Id` 헤더 미포함 | Swagger에 헤더 입력 |
| 로그인 후 세션 없음 | Redis 미실행 | `docker start redis-fastapi` |
| rebuild 후 메시지 없음 | Supabase에도 메시지 없음 | 먼저 `POST /messages`로 저장 |
| 캐시 메시지 순서 역순 | `reversed()` 미적용 | `list(reversed(result.data))` |
| 타인 메시지 접근 시 200 반환 | `get_owned_conversation` 미호출 | 모든 메시지 엔드포인트에서 소유권 확인 |
| recent와 messages 개수 불일치 | `RECENT_HISTORY_LIMIT` 초과 | 정상 동작 — 캐시는 최근 N개만 유지 |
| Redis 재시작 후 세션 모두 사라짐 | 메모리 저장이라 재시작 시 초기화 | 다시 로그인 필요 (정상 동작) |

## 최종 과제

1. `/auth/refresh` API를 추가해서 Redis에 저장된 refresh_token으로 Supabase 세션을 갱신한다.
2. `/conversations/{id}` 삭제 API를 만들고, Supabase 데이터와 Redis 캐시를 함께 삭제한다.
3. 대화방별 메시지 개수를 반환하는 `/conversations/summary` API를 구현한다.
4. 최근 대화 캐시에 `user` 메시지만 저장할지, `assistant` 메시지도 저장할지 설계 기준을 정리한다.
5. Redis 세션 만료 시 자동으로 refresh_token을 사용해 새 access_token을 발급받는 미들웨어를 작성한다.
