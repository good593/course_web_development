# 3교시: Supabase Auth 회원가입·로그인과 사용자별 접근 제어

**소요시간:** 90분 (이론 30분 + 실습 60분)  
**사전 지식:** 2교시(FastAPI + Supabase 연동), HTTP 헤더 개념

---

## 학습 목표

- Supabase Auth로 이메일/비밀번호 회원가입과 로그인을 구현한다
- JWT access_token의 구조와 용도를 설명한다
- 로그인 응답의 `access_token`을 FastAPI Bearer 인증에 사용한다
- API 서버가 current_user id를 직접 결정하도록 구조를 바꾼다
- RLS(Row Level Security) 정책의 역할을 이해한다

---

## 1. 2교시 방식의 문제

2교시에서는 URL에 `user_id`를 직접 넣었습니다.

```http
GET /users/{user_id}/conversations
```

이 방식의 문제:

```
다른 사람의 user_id를 알면?
  ↓
그 사람의 URL을 그대로 요청할 수 있음
  ↓
서버가 막을 방법 없음 (인증 없음)
  ↓
개인정보 침해 위험
```

3교시에서는 로그인 기반으로 바꿉니다.

```
1. 회원가입 → 이메일 + 비밀번호
2. 로그인 → access_token 발급
3. 요청마다 Authorization: Bearer {token} 헤더 포함
4. FastAPI가 토큰 검증 → current_user.id 결정
5. 서버 코드에서 current_user.id로만 데이터 조회
```

## 2. JWT란 무엇인가

JWT(JSON Web Token)는 서버가 발급하는 서명된 토큰입니다.

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
.eyJ1c2VyX2lkIjoieHh4IiwiZXhwIjoxNzAwMDAwMDAwfQ
.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

`.`으로 구분된 세 부분으로 이루어집니다.

| 부분 | 내용 | 특징 |
|------|------|------|
| 헤더 | 알고리즘 정보 | `{"alg": "HS256", "typ": "JWT"}` |
| 페이로드 | 사용자 정보 + 만료 시간 | `{"sub": "user-id", "exp": 1700000}` |
| 서명 | 위변조 방지 | 서버만 아는 비밀키로 생성 |

페이로드는 Base64로 인코딩되어 있어서 누구나 디코딩할 수 있습니다.  
하지만 **서명이 없으면 변조를 알아챌 수 없으므로** 서명 검증이 핵심입니다.

### access_token vs refresh_token

| 항목 | access_token | refresh_token |
|------|--------------|---------------|
| 용도 | API 요청 인증 | access_token 갱신 |
| 만료 시간 | 짧음 (기본 1시간) | 김 (기본 7일) |
| 전달 방법 | Authorization 헤더 | 안전한 저장소에만 보관 |
| 유출 시 | 짧은 시간 후 자동 만료 | 즉시 무효화 필요 |

## 3. Supabase Auth 기본 흐름

### 회원가입

```python
result = supabase.auth.sign_up({
    "email": data.email,
    "password": data.password,
})
# result.user: 생성된 사용자 정보
# result.session: 이메일 인증 전이면 None일 수 있음
```

> **이메일 인증 설정**  
> Supabase Dashboard → **Authentication → Providers → Email**  
> **"Confirm email"** 옵션을 끄면 가입 즉시 로그인할 수 있습니다.  
> 개발/테스트 중에는 끄는 것이 편리합니다.

### 로그인

```python
result = supabase.auth.sign_in_with_password({
    "email": data.email,
    "password": data.password,
})

access_token  = result.session.access_token
refresh_token = result.session.refresh_token
user_id       = str(result.user.id)
```

### 토큰으로 현재 사용자 확인

```python
result = supabase.auth.get_user(access_token)
user_id = str(result.user.id)
email   = result.user.email
```

`get_user(token)`은 토큰 서명을 검증하고 Supabase Auth에서 사용자 정보를 반환합니다.

## 4. Authorization 헤더와 HTTPBearer

### 헤더 형식

```http
Authorization: Bearer eyJhbGciOi...
```

`Bearer ` 다음에 access_token을 붙입니다. (공백 포함)

### FastAPI에서 Bearer 토큰 받기

```python
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials
from fastapi import Depends, HTTPException
from pydantic import BaseModel

security = HTTPBearer()

class CurrentUser(BaseModel):
    id: str
    email: str

def get_current_user(
    credentials: HTTPAuthorizationCredentials = Depends(security),
) -> CurrentUser:
    token = credentials.credentials  # "Bearer " 이후의 실제 토큰값

    try:
        result = public_client().auth.get_user(token)
    except Exception:
        raise HTTPException(status_code=401, detail="토큰이 유효하지 않습니다")

    return CurrentUser(
        id=str(result.user.id),
        email=result.user.email,
    )
```

엔드포인트에서는 `user_id`를 URL로 받지 않고 `current_user`를 의존성으로 받습니다.

```python
# ❌ 2교시 방식 — user_id를 URL로 받음
@app.get("/users/{user_id}/conversations")
def list_conversations(user_id: str):
    ...

# ✅ 3교시 방식 — 토큰에서 사용자 결정
@app.get("/conversations")
def list_conversations(current: CurrentUser = Depends(get_current_user)):
    # current.id로만 조회 — URL 조작 불가
    ...
```

### Swagger UI에서 Bearer 토큰 입력 방법

1. `POST /auth/login`으로 로그인 → 응답의 `access_token` 값 복사
2. Swagger UI 우측 상단 **Authorize** 버튼 클릭
3. Value 입력란에 `Bearer eyJhbGciOi...` 전체 입력 (`Bearer ` 앞에 포함)
4. **Authorize** → **Close** 클릭
5. 이후 모든 요청에 자동으로 헤더가 붙음

## 5. Auth 사용자와 서비스 테이블 연결

Supabase Auth 사용자는 `auth.users`에 자동 저장됩니다.  
프로필, 대화 등 서비스 데이터는 `public` 스키마에 별도로 만듭니다.

```
auth.users (Supabase 내부 관리)
  └── 1:1 → public.profiles      (우리가 관리)
  └── 1:N → public.chat_conversations
               └── 1:N → public.chat_messages
```

```sql
-- 프로필 테이블 (auth.users와 1:1)
create table public.profiles (
  id           uuid        primary key references auth.users(id) on delete cascade,
  email        text        not null,
  display_name text        not null,
  created_at   timestamptz not null default now()
);

-- 대화 테이블 (owner_id = auth.users.id)
create table public.chat_conversations (
  id         uuid        primary key default gen_random_uuid(),
  owner_id   uuid        not null references auth.users(id) on delete cascade,
  title      text        not null default '새 대화',
  created_at timestamptz not null default now()
);

-- 메시지 테이블
create table public.chat_messages (
  id              uuid        primary key default gen_random_uuid(),
  conversation_id uuid        not null references public.chat_conversations(id) on delete cascade,
  role            text        not null check (role in ('user', 'assistant', 'system')),
  content         text        not null,
  created_at      timestamptz not null default now()
);
```

### 회원가입 후 프로필 자동 생성

회원가입 시 `auth.users`에 계정을 만든 뒤, 우리 `profiles` 테이블에도 추가합니다.

```python
@app.post("/auth/signup", status_code=201)
def signup(data: SignupRequest):
    # 1. Supabase Auth 계정 생성
    result = public_client().auth.sign_up({
        "email": data.email,
        "password": data.password,
    })
    user_id = str(result.user.id)

    # 2. 서비스 프로필 테이블에도 추가
    admin_client().table("profiles").insert({
        "id": user_id,
        "email": data.email,
        "display_name": data.display_name,
    }).execute()

    return {"user_id": user_id, "email": data.email}
```

## 6. 두 종류의 Supabase 클라이언트

이번 교시부터 클라이언트를 역할에 따라 나눕니다.

```python
def public_client() -> Client:
    """anon 키 — Auth 작업(로그인, 회원가입, 토큰 검증)에 사용"""
    return create_client(SUPABASE_URL, SUPABASE_ANON_KEY)

def admin_client() -> Client:
    """service_role 키 — 데이터 CRUD에 사용"""
    return create_client(SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY)
```

| 작업 | 클라이언트 | 이유 |
|------|-----------|------|
| `auth.sign_up()` | `public_client()` | Auth API는 anon 키로 호출 |
| `auth.sign_in_with_password()` | `public_client()` | Auth API |
| `auth.get_user(token)` | `public_client()` | 토큰 검증도 Auth API |
| `table("profiles").insert()` | `admin_client()` | DB 쿼리는 service_role |
| `table("chat_conversations").select()` | `admin_client()` | DB 쿼리 |

---

## 7. 서버 측 접근 제어

`service_role` 키는 RLS를 우회합니다. 따라서 서버 코드에서 반드시 소유자 필터를 붙여야 합니다.

```python
# ❌ 소유자 확인 없음 — 모든 사용자의 대화가 반환됨
result = (
    admin_client()
    .table("chat_conversations")
    .select("*")
    .execute()
)

# ✅ 현재 사용자의 대화만 반환
result = (
    admin_client()
    .table("chat_conversations")
    .select("*")
    .eq("owner_id", current.id)   # 반드시 필요!
    .order("created_at", desc=True)
    .execute()
)
```

### 메시지 저장 시 대화 소유권 확인

```python
def get_owned_conversation(conversation_id: str, user_id: str) -> dict:
    result = (
        admin_client()
        .table("chat_conversations")
        .select("*")
        .eq("id", conversation_id)
        .eq("owner_id", user_id)  # 내 대화인지 확인
        .limit(1)
        .execute()
    )
    if not result.data:
        raise HTTPException(404, "대화방을 찾을 수 없습니다")
    return result.data[0]
```

## 8. RLS(Row Level Security) 정책

RLS는 DB 레벨에서 행 단위 접근을 통제합니다.  
서버 코드의 실수를 DB 레벨에서 방어선으로 막을 수 있습니다.

```sql
-- RLS 활성화
alter table public.chat_conversations enable row level security;

-- SELECT 정책: 자신의 대화만 조회 가능
create policy "conversations_select_own"
on public.chat_conversations for select
to authenticated
using ((select auth.uid()) = owner_id);

-- INSERT 정책: 자신의 owner_id로만 삽입 가능
create policy "conversations_insert_own"
on public.chat_conversations for insert
to authenticated
with check ((select auth.uid()) = owner_id);

-- DELETE 정책: 자신의 대화만 삭제 가능
create policy "conversations_delete_own"
on public.chat_conversations for delete
to authenticated
using ((select auth.uid()) = owner_id);
```

### 두 가지 접근 방식 비교

| 접근 방식 | 키 | 접근 제어 위치 |
|----------|---|--------------------|
| FastAPI 서버 (이번 실습) | `service_role` | 서버 코드 `.eq("owner_id", current.id)` |
| 프론트엔드 직접 Supabase 호출 | `anon` + user JWT | DB의 RLS 정책 |

실무에서는 **두 레이어를 함께 유지**합니다.  
서버 코드가 실수해도 RLS가 방어해 주고, RLS가 없어도 서버 코드가 막아줍니다.

## 9. 이번 교시 API

```
POST  /auth/signup
POST  /auth/login
GET   /me
PATCH /me
POST  /conversations
GET   /conversations
POST  /conversations/{conversation_id}/messages
GET   /conversations/{conversation_id}/messages
```

### 실습 순서

1. Supabase SQL Editor에서 `schema.sql` 실행
2. **Authentication → Providers → Email** → **"Confirm email"** 끄기
3. `.env`에 `SUPABASE_ANON_KEY` 추가
4. `POST /auth/signup`으로 사용자 A 가입
5. `POST /auth/login`으로 로그인 → 응답의 `access_token` 복사
6. Swagger **Authorize** → `Bearer {access_token}` 입력
7. `GET /me` → 자신의 프로필 확인
8. `POST /conversations` → 대화방 생성
9. `POST /conversations/{id}/messages` → 메시지 저장
10. 사용자 B로 회원가입/로그인 후 A의 대화가 보이지 않는지 확인

## 10. 흔한 실수와 해결법

| 오류 | 원인 | 해결 |
|------|------|------|
| `401 Could not validate credentials` | 토큰 만료 또는 잘못된 형식 | 다시 로그인 후 새 토큰 사용 |
| Swagger `401` 계속 발생 | `Bearer ` 접두사 누락 | `Bearer eyJ...` 전체 입력 |
| 회원가입 후 로그인 불가 | 이메일 인증이 켜져 있음 | Authentication → Email → "Confirm email" 끄기 |
| `profiles` 테이블 insert 오류 | `schema.sql` 미실행 | SQL Editor에서 `schema.sql` 재실행 |
| 타인 대화방 접근 시 200 반환 | `.eq("owner_id", ...)` 누락 | `get_owned_conversation` 함수 사용 |
| `422` on signup | email 형식 오류 또는 password 짧음 | 올바른 email + 6자 이상 password |
| `profiles` insert 실패 | `SUPABASE_ANON_KEY` 없음 | `.env`에 anon key 추가 |
| access_token 만료 | 1시간 경과 | 다시 `POST /auth/login` 호출 |
