# 2교시: FastAPI와 Supabase 연동

**소요시간:** 90분 (이론 25분 + 실습 65분)  
**사전 지식:** 1교시(Supabase 스키마), FastAPI Pydantic, 의존성 주입(5교시)

---

## 학습 목표

- FastAPI 서버에서 Supabase를 외부 데이터 저장소로 사용한다
- 환경 변수로 Supabase URL과 서버 키를 안전하게 분리한다
- Pydantic 스키마, Repository, 엔드포인트의 역할을 구분한다
- 사용자 정보와 서비스 데이터를 저장, 수정(PATCH), 조회한다
- Supabase 응답의 `data`를 FastAPI 응답으로 변환한다

---

## 1. 1교시와 2교시의 차이

1교시에서는 기본적인 저장과 조회만 구현했습니다. 2교시에서는 코드 구조를 개선하고 실제 서비스처럼 CRUD를 완성합니다.

| 비교 | 1교시 | 2교시 |
|------|-------|-------|
| 코드 구조 | `main.py`에 모두 작성 | Pydantic / Repository / Endpoint 분리 |
| 지원 연산 | CREATE, READ | CREATE, READ, UPDATE (PATCH) |
| 오류 처리 | 기본 404 | 404, 422, FK 오류 사전 방지 |
| 사용자 식별 | user_id를 URL로 직접 전달 | (여전히 URL로) → 3교시에서 Auth로 대체 |
| 집계 API | 없음 | `/summary` — 대화 수·메시지 수 |

## 2. 전체 구조

```
[Swagger UI / Client]
        ↓ HTTP 요청
[FastAPI 엔드포인트]     ← 경로, 상태 코드, 의존성 주입
        ↓ Pydantic 검증
[SupabaseRepository]     ← Supabase 쿼리 로직 모음
        ↓ supabase-py
[Supabase Data API]
        ↓
[PostgreSQL Tables]
```

각 레이어의 책임을 명확히 구분합니다.

| 레이어 | 담당 |
|--------|------|
| Pydantic Schema | 요청 바디 형식 검증 |
| Repository | Supabase 테이블 쿼리 로직 |
| Endpoint | HTTP 경로, 상태 코드, 의존성 주입 |
| Supabase | PostgreSQL 저장 + Data API |

## 4. Pydantic 스키마 설계

FastAPI는 요청이 들어오면 Pydantic으로 먼저 형식을 검사합니다.

```python
from pydantic import BaseModel, Field
from typing import Literal, Optional

class UserCreate(BaseModel):
    username: str = Field(..., min_length=2, max_length=30)
    display_name: str = Field(..., min_length=1, max_length=50)

class UserUpdate(BaseModel):
    display_name: Optional[str] = Field(None, min_length=1, max_length=50)

class ConversationCreate(BaseModel):
    title: str = Field("새 대화", min_length=1, max_length=100)

class ConversationUpdate(BaseModel):
    title: Optional[str] = Field(None, min_length=1, max_length=100)

class MessageCreate(BaseModel):
    role: Literal["user", "assistant", "system"]
    content: str = Field(..., min_length=1, max_length=2000)
```

### 검증 실패 시 자동 422 응답

| 잘못된 입력 | Pydantic 오류 | HTTP 응답 |
|------------|--------------|-----------|
| `username: "a"` | min_length=2 위반 | 422 |
| `role: "bot"` | Literal 위반 | 422 |
| `content: ""` | min_length=1 위반 | 422 |
| `username` 누락 | required field | 422 |

422 응답 형식:

```json
{
  "detail": [
    {
      "type": "string_too_short",
      "loc": ["body", "username"],
      "msg": "String should have at least 2 characters",
      "input": "a"
    }
  ]
}
```

## 5. Repository 패턴

Repository는 데이터 접근 코드를 한 곳에 모아서 엔드포인트를 깔끔하게 만드는 패턴입니다.

### Repository 없이 작성하면

```python
# ❌ 엔드포인트에 쿼리 로직이 직접 들어감
@app.post("/users", status_code=201)
def create_user(data: UserCreate):
    result = (
        supabase.table("app_users")
        .insert(data.model_dump())
        .select("*")
        .execute()
    )
    if not result.data:
        raise HTTPException(500, "저장 실패")
    return result.data[0]

@app.get("/users/{user_id}")
def get_user(user_id: str):
    result = (
        supabase.table("app_users")
        .select("*")
        .eq("id", user_id)
        .execute()
    )
    if not result.data:
        raise HTTPException(404, "사용자 없음")
    return result.data[0]
# 엔드포인트마다 같은 패턴 반복...
```

### Repository로 분리하면

```python
# ✅ Repository 클래스에 쿼리 로직을 모음
class SupabaseRepository:
    def __init__(self, db: Client):
        self.db = db

    def create_user(self, data: UserCreate) -> dict:
        result = (
            self.db.table("app_users")
            .insert(data.model_dump())
            .select("*")
            .execute()
        )
        return one_or_404(result.data, "사용자가 생성되지 않았습니다")

    def get_user(self, user_id: str) -> dict:
        result = (
            self.db.table("app_users")
            .select("*")
            .eq("id", user_id)
            .execute()
        )
        return one_or_404(result.data, "사용자를 찾을 수 없습니다")

    def update_user(self, user_id: str, data: UserUpdate) -> dict:
        # None인 필드는 제외 (PATCH 의미)
        payload = {k: v for k, v in data.model_dump().items() if v is not None}
        result = (
            self.db.table("app_users")
            .update(payload)
            .eq("id", user_id)
            .select("*")
            .execute()
        )
        return one_or_404(result.data, "사용자를 찾을 수 없습니다")
```

엔드포인트 코드는 훨씬 짧아집니다.

```python
# ✅ 엔드포인트는 경로와 흐름만 담당
@app.post("/users", status_code=201)
def create_user(data: UserCreate, repo: SupabaseRepository = Depends(get_repo)):
    return repo.create_user(data)

@app.get("/users/{user_id}")
def get_user(user_id: str, repo: SupabaseRepository = Depends(get_repo)):
    return repo.get_user(user_id)

@app.patch("/users/{user_id}")
def update_user(user_id: str, data: UserUpdate, repo: SupabaseRepository = Depends(get_repo)):
    return repo.update_user(user_id, data)
```

## 6. 의존성 주입으로 Repository 공유

`Depends`를 사용하면 Repository를 요청마다 새로 만들지 않아도 됩니다.

```python
def get_repo() -> SupabaseRepository:
    """요청마다 Repository 인스턴스를 만들어 주입"""
    return SupabaseRepository(supabase)
```

엔드포인트에서 다음처럼 사용합니다.

```python
@app.get("/users/{user_id}")
def get_user(
    user_id: str,
    repo: SupabaseRepository = Depends(get_repo),
):
    return repo.get_user(user_id)
```

### SQLAlchemy와 Supabase 비교

13교시(CRUD 서비스 구현)에서는 SQLAlchemy 세션을 Repository에 넣었습니다. Supabase는 방식이 다릅니다.

| 작업 | SQLAlchemy | Supabase Python |
|------|------------|-----------------|
| 테이블 선택 | `db.query(User)` | `.table("app_users")` |
| 조건 | `.filter(User.id == id)` | `.eq("id", id)` |
| 저장 | `db.add(obj); db.commit()` | `.insert(payload).execute()` |
| 수정 | `obj.field = val; db.commit()` | `.update(payload).eq(...).execute()` |
| 삭제 | `db.delete(obj); db.commit()` | `.delete().eq(...).execute()` |
| 정렬 | `.order_by(Model.field)` | `.order("field")` |
| 결과 | ORM 객체 리스트 | `dict` 리스트 |

## 7. PATCH vs PUT

| 메서드 | 의미 | 동작 |
|--------|------|------|
| PUT | 전체 교체 | 모든 필드를 다시 보내야 함 |
| PATCH | 부분 수정 | 바꿀 필드만 보내도 됨 |

PATCH를 위한 Supabase 수정 패턴:

```python
def update_user(self, user_id: str, data: UserUpdate) -> dict:
    # None인 필드 제외 — 보내지 않은 필드는 그대로 유지
    payload = {k: v for k, v in data.model_dump().items() if v is not None}

    if not payload:
        # 바꿀 내용이 없으면 현재 데이터 그대로 반환
        return self.get_user(user_id)

    result = (
        self.db.table("app_users")
        .update(payload)
        .eq("id", user_id)
        .select("*")   # 수정 후 변경된 값 반환
        .execute()
    )
    return one_or_404(result.data, "사용자를 찾을 수 없습니다")
```

PUT 방식으로 구현하면 `display_name`만 바꿔도 `username`도 함께 보내야 합니다. PATCH는 바꿀 것만 보내면 됩니다.

## 8. 관계 데이터 저장 시 소유권 확인

대화방을 만들기 전에 사용자가 실제로 존재하는지 확인합니다.

```python
# ❌ 확인 없이 바로 저장
def create_conversation(self, user_id: str, data: ConversationCreate) -> dict:
    payload = data.model_dump() | {"user_id": user_id}
    result = self.db.table("conversations").insert(payload).select("*").execute()
    return result.data[0]
    # 존재하지 않는 user_id면 FK 오류 발생 → DB 오류 메시지 그대로 노출
```

```python
# ✅ 사용자 존재 확인 후 저장
def create_conversation(self, user_id: str, data: ConversationCreate) -> dict:
    self.get_user(user_id)  # 없으면 404 발생

    payload = data.model_dump() | {"user_id": user_id}
    result = (
        self.db.table("conversations")
        .insert(payload)
        .select("*")
        .execute()
    )
    return one_or_404(result.data, "대화방 생성 실패")
```

사전 확인 없이도 DB FK가 막아주지만, 사용자는  
`"FK_violation: user_id not found"` 보다  
`"사용자를 찾을 수 없습니다"` 메시지를 받는 편이 훨씬 낫습니다.

## 9. 404 헬퍼 함수

매번 같은 패턴을 반복하지 않도록 헬퍼 함수를 만듭니다.

```python
def one_or_404(rows: list[dict], detail: str) -> dict:
    if not rows:
        raise HTTPException(status_code=404, detail=detail)
    return rows[0]
```

사용 예:

```python
result = self.db.table("app_users").select("*").eq("id", user_id).execute()
return one_or_404(result.data, "사용자를 찾을 수 없습니다")
```

## 10. 이번 교시 API

```
POST  /users                              — 사용자 생성
GET   /users/{user_id}                    — 특정 사용자 조회
PATCH /users/{user_id}                    — 사용자 정보 수정
POST  /users/{user_id}/conversations      — 대화방 생성
GET   /users/{user_id}/conversations      — 사용자별 대화 목록
PATCH /conversations/{conversation_id}    — 대화 제목 수정
POST  /conversations/{conversation_id}/messages  — 메시지 저장
GET   /conversations/{conversation_id}/messages  — 메시지 목록
GET   /users/{user_id}/summary            — 대화 수·메시지 수 요약
```

### 실습 순서

1. `schema.sql`을 Supabase SQL Editor에서 실행
2. `POST /users`로 사용자 **A**, **B** 각각 생성
3. 사용자 A의 id로 `POST /users/{id}/conversations` 대화방 2개 생성
4. 각 대화방에 `user`/`assistant` 메시지 번갈아 저장
5. `GET /users/{id}/summary`에서 대화 수와 메시지 수 확인
6. `PATCH /users/{id}` → `{"display_name": "김강사"}` 수정 후 확인
7. 사용자 B의 id로 같은 API를 호출 → 데이터가 B 것만 보이는지 확인

## 11. 현재 방식의 보안 한계

이번 교시는 아직 로그인이 없어서 `user_id`를 URL에 직접 넣습니다.

```
GET /users/{user_id}/conversations
```

이 방식은 학습에는 좋지만 실제 서비스에서는 위험합니다.

```
다른 사람의 user_id를 알면?
  ↓
그 사람의 대화 목록을 요청할 수 있음
  ↓
개인정보 침해!
```

3교시에서는 Supabase Auth로 해결합니다.

```
로그인 → access_token 발급
  ↓
FastAPI가 토큰으로 current_user.id 확인
  ↓
URL에 user_id 불필요 — 서버가 직접 결정
```

## 12. 흔한 실수와 해결법

| 오류 | 원인 | 해결 |
|------|------|------|
| `PATCH` 후에도 이전 데이터 반환 | `.select("*")` 누락 | `.update(...).select("*").execute()` |
| `result.data`가 빈 리스트인데 오류 없음 | 업데이트할 id가 존재하지 않음 | `one_or_404` 함수로 404 처리 |
| 대화방 생성 시 404 | user_id 오타 또는 없는 사용자 | `GET /users/{id}`로 먼저 존재 확인 |
| 한 필드만 변경했는데 다른 필드가 null | None 필터링 미적용 | `{k: v for k, v in d.items() if v is not None}` |
| `422` on MessageCreate | role 값 오류 | `user`, `assistant`, `system` 중 하나 |
| summary API 값이 0 | user_id와 conversations의 FK 불일치 | Supabase Table Editor에서 직접 확인 |
| `.env`가 로드되지 않음 | `load_dotenv()` 호출 위치 문제 | 파일 최상단에서 `load_dotenv()` 호출 |
