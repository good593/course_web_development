# 1교시: Supabase 프로젝트 설정과 ERD 설계

**소요시간:** 60분 (이론 20분 + 실습 40분)
**사전 지식:** PostgreSQL 기초(테이블, PK/FK, 제약 조건), Python 기초

---

## 학습 목표

- AI 대화 서비스의 ERD를 3개 테이블로 설계한다
- `on delete cascade`, `CHECK` 등 제약 조건을 설계에 반영하는 이유를 설명한다
- Supabase 프로젝트를 생성하고 API 키를 확인한다
- `service_role` 키와 `anon` 키의 용도와 보안 규칙을 구분한다

---

> 이 강의에서 사용하는 Supabase의 RDB는 **PostgreSQL**입니다. 앞으로 작성하는 SQL과 스키마는 PostgreSQL 문법을 그대로 사용합니다.

## 1. 대화 서비스 ERD 설계

이번 과정 전체에서 사용할 도메인: **사용자별 AI 대화 서비스**

### ERD (Entity-Relationship Diagram)

```
app_users          conversations          messages
    │                    │                    │
    │   1 : N            │   1 : N            │
    └───────────────────►│                    │
                         └───────────────────►│
```

- 1명의 사용자 → N개의 대화방 (1:N)
- 1개의 대화방 → N개의 메시지 (1:N)

---
### 각 테이블의 역할

```
app_users
  id           UUID        PK — 사용자 고유 식별자
  username     TEXT        NOT NULL UNIQUE — 로그인용 이름
  display_name TEXT        NOT NULL — 화면에 보이는 이름
  created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()

conversations
  id           UUID        PK — 대화방 고유 식별자
  user_id      UUID        FK → app_users.id — 누구의 대화방인가
  title        TEXT        NOT NULL DEFAULT '새 대화'
  created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()

messages
  id              UUID        PK — 메시지 고유 식별자
  conversation_id UUID        FK → conversations.id — 어느 대화방의 메시지인가
  role            TEXT        NOT NULL CHECK (role IN ('user','assistant','system'))
  content         TEXT        NOT NULL — 메시지 내용
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
```

---

### 설계 결정 이유

| 결정 | 이유 |
|------|------|
| 사용자/대화/메시지를 3개 테이블로 분리 | 각자 독립적으로 수정 가능, 데이터 중복 제거 |
| `role` 컬럼으로 구분 | OpenAI API 형식과 동일 — LLM에 바로 전달 가능 |
| `created_at` 저장 | 메시지 순서 복원, 최신 대화 정렬에 필수 |
| `id`를 UUID로 | 여러 서버에서 동시 생성해도 충돌 없음, Supabase Auth(`auth.users.id`)와 자연스럽게 연동 |
| `on delete cascade` | 사용자 삭제 시 대화방·메시지 자동 삭제 |
| `CHECK (role IN (...))` | DB 레벨에서 잘못된 role 저장 차단 |

## 2. 외래 키와 ON DELETE CASCADE

```sql
user_id UUID NOT NULL REFERENCES app_users(id) ON DELETE CASCADE
```

사용자를 삭제하면:

```
DELETE app_users WHERE id = 'u1'
  ↓ cascade
  conversations WHERE user_id = 'u1' → 자동 삭제
    ↓ cascade
    messages WHERE conversation_id IN (...) → 자동 삭제
```

`ON DELETE CASCADE`가 없다면 FK를 참조하는 하위 데이터가 있는 한 삭제가 거부됩니다.
직접 삭제하려면 messages → conversations → app_users 순서로 삭제해야 합니다.

## [3. Supabase란](https://supabase.com/)

Supabase는 **오픈소스 Firebase 대안**으로, PostgreSQL 데이터베이스와 인증·저장소·실시간 구독 기능을 함께 제공합니다.

---
이 과정에서 Supabase를 선택하는 이유:

| 이유 | 설명 |
|------|------|
| PostgreSQL 사용 | 업계 표준 RDBMS, 학습한 내용이 그대로 실무로 이어짐 |
| REST API 자동 생성 | Python 클라이언트(supabase-py)로 바로 사용 가능 |
| Auth 내장 | 회원가입·로그인을 직접 구현하지 않아도 됨 (6교시) |
| [무료 플랜](https://supabase.com/pricing) | 개인 프로젝트·학습에 충분 |
| 대시보드 | SQL Editor, Table Editor 등 시각적 도구 제공 |

## 핵심 개념 요약

| 개념 | 핵심 |
|------|------|
| ERD | 1명의 사용자 → N개의 대화방 → N개의 메시지 |
| FK + ON DELETE CASCADE | 부모 삭제 시 자식 데이터 연쇄 삭제 |
