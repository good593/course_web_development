# 8교시: Redis 세션 관리와 Supabase 통합

**소요시간:** 120분 (환경 준비 20분 + 이론 30분 + 실습 70분)  
**사전 지식:** 7교시(Supabase Auth + RLS), Redis 자료구조·TTL 개념

---

## 학습 목표

- Redis 클라이언트를 초기화하고 `decode_responses`, 키 이름 설계 같은 FastAPI 연동 시 주의사항을 적용한다
- Supabase Auth 로그인 결과를 Redis 앱 세션으로 변환하는 흐름을 구현한다
- Redis 세션과 Supabase access_token을 이중으로 검증하는 의존성을 작성한다
- 메시지를 Supabase(영구)와 Redis(캐시) 두 곳에 나눠 저장하는 이유를 설명한다
- Redis 캐시가 삭제된 경우 Supabase에서 복구(rebuild)하는 엔드포인트를 구현한다
- 전체 데이터 흐름을 회원가입부터 캐시 조회까지 단계별로 추적한다

---

> Redis의 자료구조(String/Hash/List/Set/TTL)는 이미 안다는 전제로 진행합니다. 이 교시는 "Redis를 FastAPI·Supabase와 어떻게 엮는가"에 집중합니다.

## 1. Redis 환경 준비와 FastAPI 연동 시 주의사항

### Docker로 Redis 실행

```bash
docker run --name redis-fastapi -p 6379:6379 -d redis:7
docker exec -it redis-fastapi redis-cli ping   # PONG
docker stop redis-fastapi
docker start redis-fastapi
```

### Python 클라이언트 초기화 — decode_responses

```python
import redis

r = redis.from_url(
    "redis://localhost:6379/0",
    decode_responses=True,   # bytes → str 자동 변환
)
r.ping()  # True
```

`decode_responses=True`가 없으면 모든 값이 `bytes`로 반환되어 JSON 파싱·딕셔너리 비교 시 `AttributeError: 'bytes' object`가 발생합니다.

### 키 이름 설계

```
권장 패턴: {도메인}:{식별자}

app_session:{session_id}                 → 앱 세션 Hash
recent_history:{user_id}:{conversation_id} → 최근 대화 캐시 List
```

```bash
KEYS app_session:*      # 키 목록 (운영 환경에서 사용 금지!)
TYPE app_session:abc    # hash
DEL app_session:abc     # 키 삭제
```

## 2. 전체 아키텍처

```
[클라이언트]
     │
     │ 로그인 (email + password)
     ▼
[FastAPI] ──────────────────────► Supabase Auth
     │                              access_token 발급
     │ session_id 반환
     │ (access_token은 서버만 보관)
     ▼
[Redis]                        [Supabase PostgreSQL]
app_session:{id}               profiles (영구)
  user_id                      chat_conversations (영구)
  access_token                 chat_messages (영구)
  created_at
recent_history:{uid}:{conv_id}  ← 최근 N개 캐시
```

### Supabase vs Redis 역할 분리

| 데이터 | 저장 위치 | 이유 |
|--------|-----------|------|
| 회원 계정 | Supabase Auth | 인증 전용 시스템 |
| 프로필, 대화, 메시지 | Supabase PostgreSQL | 영구 보관 필요 |
| 앱 세션 | Redis | TTL 자동 만료, 빠른 조회 |
| 최근 대화 캐시 | Redis | LLM 컨텍스트용 빠른 읽기 |

## 3. 로그인 흐름 — Auth → 앱 세션

Supabase Auth 로그인 결과를 Redis에 저장하고 자체 `session_id`를 발급합니다.

```python
@app.post("/auth/login")
def login(data: LoginRequest):
    # 1. Supabase Auth로 이메일/비밀번호 검증
    result = public_client().auth.sign_in_with_password({
        "email": data.email,
        "password": data.password,
    })

    user_id       = str(result.user.id)
    access_token  = result.session.access_token
    refresh_token = result.session.refresh_token

    # 2. Redis에 앱 세션 저장 (access_token 포함)
    session_id = str(uuid4())
    key = f"app_session:{session_id}"
    r.hset(key, mapping={
        "user_id":       user_id,
        "email":         result.user.email,
        "access_token":  access_token,
        "refresh_token": refresh_token,
        "created_at":    int(time.time()),
        "last_seen_at":  int(time.time()),
    })
    r.expire(key, SESSION_TTL_SECONDS)

    # 3. 클라이언트에게는 session_id만 반환 (access_token 노출 안 함)
    return {"session_id": session_id, "user_id": user_id}
```

이후 모든 요청에서 클라이언트는 `session_id`만 보냅니다:

```http
X-Session-Id: 58f2a3d1-1234-5678-abcd-...
```

`access_token`은 Redis 안에만 있으므로 클라이언트에 노출되지 않습니다.

## 4. 이중 검증 — Redis 세션 + Supabase 토큰

Redis 세션이 있다고 해서 무조건 신뢰하면 안 됩니다.  
세션 안의 Supabase `access_token`도 유효한지 함께 검증합니다.

```python
def get_current_session(
    x_session_id: str | None = Header(default=None, alias="X-Session-Id"),
) -> AppSession:
    if not x_session_id:
        raise HTTPException(401, "X-Session-Id 헤더가 필요합니다")

    key = f"app_session:{x_session_id}"
    data = r.hgetall(key)

    # 1단계: Redis 세션 존재 확인
    if not data:
        raise HTTPException(401, "세션이 없거나 만료되었습니다. 다시 로그인하세요.")

    # 2단계: Supabase access_token 검증
    try:
        auth_result = public_client().auth.get_user(data["access_token"])
    except Exception:
        r.delete(key)  # 유효하지 않은 세션 즉시 삭제
        raise HTTPException(401, "토큰이 만료되었습니다. 다시 로그인하세요.")

    # 3단계: user_id 일치 확인 (변조 방지)
    if str(auth_result.user.id) != data["user_id"]:
        r.delete(key)
        raise HTTPException(401, "세션 사용자 정보가 일치하지 않습니다")

    # 4단계: TTL 갱신 (Sliding Expiry)
    r.expire(key, SESSION_TTL_SECONDS)
    r.hset(key, "last_seen_at", int(time.time()))

    return AppSession(
        session_id=x_session_id,
        user_id=data["user_id"],
        email=data["email"],
        access_token=data["access_token"],
    )
```

### 검증 단계 요약

| 단계 | 확인 내용 | 실패 시 |
|------|----------|---------|
| 1 | Redis 세션 존재 | 401 + 재로그인 안내 |
| 2 | Supabase access_token 유효성 | 세션 삭제 + 401 |
| 3 | Redis user_id == Auth user_id | 세션 삭제 + 401 |
| 4 | TTL 갱신 | - |

## 5. 메시지 이중 저장 — Supabase 먼저

메시지를 영구 저장소(Supabase)와 캐시(Redis) 두 곳에 저장합니다.

### 저장 순서가 중요한 이유

```
❌ Redis 먼저 → Supabase 실패
   Redis에는 있지만 Supabase에는 없음
   서버 재시작 후 캐시 만료 → 메시지 영구 유실!

✅ Supabase 먼저 → Redis 실패
   Supabase에 원본이 있으므로
   POST /recent/rebuild 로 캐시 복구 가능
```

```python
@app.post("/conversations/{conversation_id}/messages", status_code=201)
def create_message(
    conversation_id: str,
    data: MessageCreate,
    session: AppSession = Depends(get_current_session),
):
    # 소유권 확인
    get_owned_conversation(conversation_id, session.user_id)

    # 1. Supabase에 영구 저장 (반드시 성공해야 함)
    result = (
        admin_client()
        .table("chat_messages")
        .insert({
            "conversation_id": conversation_id,
            "owner_id":        session.user_id,
            "role":            data.role,
            "content":         data.content,
        })
        .execute()
    )
    message = one_or_404(result.data, "메시지 저장 실패")

    # 2. Redis 캐시 저장 (실패해도 원본은 Supabase에 있음)
    cache_key = f"recent_history:{session.user_id}:{conversation_id}"
    r.rpush(cache_key, json.dumps(message, ensure_ascii=False))
    r.ltrim(cache_key, -RECENT_HISTORY_LIMIT, -1)
    r.expire(cache_key, RECENT_HISTORY_TTL_SECONDS)

    return message
```

## 6. 두 가지 조회 엔드포인트

| 엔드포인트 | 데이터 소스 | 특징 |
|-----------|-----------|------|
| `GET /conversations/{id}/messages` | Supabase | 전체 이력, 느릴 수 있음 |
| `GET /conversations/{id}/recent` | Redis | 최근 N개만, 초고속 |

```python
@app.get("/conversations/{conversation_id}/recent")
def get_recent(
    conversation_id: str,
    session: AppSession = Depends(get_current_session),
):
    get_owned_conversation(conversation_id, session.user_id)
    key = f"recent_history:{session.user_id}:{conversation_id}"
    return [json.loads(m) for m in r.lrange(key, 0, -1)]
```

## 7. 캐시 복구 (Rebuild)

Redis 캐시가 만료되거나 서버 재시작으로 사라지면,  
Supabase의 영구 데이터로 캐시를 다시 채웁니다.

```python
@app.post("/conversations/{conversation_id}/recent/rebuild")
def rebuild_recent(
    conversation_id: str,
    session: AppSession = Depends(get_current_session),
):
    get_owned_conversation(conversation_id, session.user_id)

    # 1. Supabase에서 최근 메시지 조회
    result = (
        admin_client()
        .table("chat_messages")
        .select("*")
        .eq("conversation_id", conversation_id)
        .eq("owner_id", session.user_id)
        .order("created_at", desc=True)
        .limit(RECENT_HISTORY_LIMIT)
        .execute()
    )
    messages = list(reversed(result.data))  # 오래된 것부터 순서 복원

    # 2. Redis 캐시 재생성
    cache_key = f"recent_history:{session.user_id}:{conversation_id}"
    r.delete(cache_key)
    for msg in messages:
        r.rpush(cache_key, json.dumps(msg, ensure_ascii=False))
    if messages:
        r.expire(cache_key, RECENT_HISTORY_TTL_SECONDS)

    return {"rebuilt": len(messages)}
```

### 왜 reversed가 필요한가

```
Supabase에서 최신순으로 조회:
  order("created_at", desc=True) → [msg5, msg4, msg3, msg2, msg1]

Redis List는 오래된 것부터 순서대로 저장해야 함:
  list(reversed(...)) → [msg1, msg2, msg3, msg4, msg5]

RPUSH 순서대로 넣으면:
  List: [msg1, msg2, msg3, msg4, msg5]  ← 올바른 순서
```

## 8. 전체 데이터 흐름 총정리

```
회원가입
  POST /auth/signup
  ├── Supabase Auth: auth.users 생성
  └── Supabase PostgreSQL: profiles 생성

로그인
  POST /auth/login
  ├── Supabase Auth: 이메일/비밀번호 검증 → access_token 발급
  └── Redis: app_session:{session_id} 저장 (access_token + user_id + email)

대화방 생성
  POST /conversations (X-Session-Id 헤더)
  ├── Redis: 세션 확인 + Supabase 토큰 검증 (이중 검증)
  └── Supabase PostgreSQL: chat_conversations 저장

메시지 저장
  POST /conversations/{id}/messages
  ├── Redis: 이중 검증
  ├── Supabase PostgreSQL: chat_messages 영구 저장
  └── Redis: recent_history 캐시 저장

최근 대화 조회
  GET /conversations/{id}/recent
  ├── Redis: 이중 검증
  └── Redis: recent_history 즉시 반환 (빠름)

전체 대화 조회
  GET /conversations/{id}/messages
  ├── Redis: 이중 검증
  └── Supabase PostgreSQL: 전체 이력 조회

캐시 복구
  POST /conversations/{id}/recent/rebuild
  ├── Redis: 이중 검증
  ├── Supabase PostgreSQL: 최근 N개 조회
  └── Redis: recent_history 재생성

로그아웃
  POST /auth/logout
  └── Redis: app_session 삭제
```

## 9. 장애 상황 대응

| 상황 | 증상 | 대응 |
|------|------|------|
| Redis 세션 만료 | `401` — 다시 로그인 | `POST /auth/login` |
| Supabase access_token 만료 | `401` — 세션 자동 삭제 | 재로그인 |
| Redis 캐시 만료 | `/recent` 빈 배열 | `POST /recent/rebuild` |
| Redis 서버 재시작 | 모든 세션 사라짐 | 재로그인 (정상 동작) |
| Supabase 저장 실패 | `500` | Redis도 저장 안 함 |

### access_token 자동 갱신 (심화)

```python
# Redis에 저장된 refresh_token으로 새 access_token 발급
result = public_client().auth.refresh_session(data["refresh_token"])
new_access_token = result.session.access_token

# Redis 세션 업데이트
r.hset(key, "access_token", new_access_token)
r.expire(key, SESSION_TTL_SECONDS)
```

## 10. 이번 교시 API

```
GET   /health
POST  /auth/signup
POST  /auth/login
POST  /auth/logout
GET   /me
POST  /conversations
GET   /conversations
POST  /conversations/{conversation_id}/messages
GET   /conversations/{conversation_id}/messages
GET   /conversations/{conversation_id}/recent
POST  /conversations/{conversation_id}/recent/rebuild
```

### 실습 순서

1. Redis 서버 실행 확인 (`docker start redis-fastapi` + ping 확인)
2. Supabase SQL Editor에서 `schema.sql` 실행
3. `POST /auth/signup` → 사용자 A, B 각각 가입
4. `POST /auth/login` (A) → `session_id` 복사
5. `X-Session-Id: {session_id}` 헤더로 모든 이후 요청
6. `GET /me` → 프로필 확인
7. `POST /conversations` → 대화방 2개 생성
8. `POST /conversations/{id}/messages` → 메시지 5개 저장
9. `GET /conversations/{id}/messages` (Supabase 전체) vs `GET /recent` (Redis) 비교
10. Redis CLI: `DEL recent_history:{uid}:{conv_id}` → 캐시 삭제
11. `GET /recent` → 빈 배열 확인
12. `POST /recent/rebuild` → 복구 후 `GET /recent` 재확인
13. B로 로그인 → A 대화방 접근 → 404 확인

## 11. 흔한 실수와 해결법

| 오류 | 원인 | 해결 |
|------|------|------|
| `401` on every request | `X-Session-Id` 헤더 미포함 | 헤더 추가 |
| 로그인 후 세션 없음 | Redis 미실행 | `docker start redis-fastapi` |
| rebuild 후 메시지 없음 | Supabase에도 메시지 없음 | 먼저 메시지 저장 후 rebuild |
| 캐시 메시지 역순 | `reversed()` 미적용 | `list(reversed(result.data))` |
| 타인 메시지 200 반환 | `get_owned_conversation` 누락 | 모든 메시지 엔드포인트에서 소유권 확인 |
| `/recent`와 `/messages` 개수 불일치 | 정상 — 캐시는 최근 N개만 | `RECENT_HISTORY_LIMIT` 설정 확인 |
| access_token 만료 → 401 | 1시간 경과 | 재로그인 |

## 최종 과제

1. `/auth/refresh` API를 추가해 Redis의 `refresh_token`으로 새 `access_token`을 발급받고 Redis 세션을 갱신한다.
2. `/conversations/{id}` DELETE API를 구현하고 Supabase 데이터와 Redis 캐시를 함께 삭제한다.
3. `GET /conversations/summary` — 현재 사용자의 전체 대화 수와 메시지 수를 반환한다.
4. Redis 세션 만료 시 `refresh_token`으로 자동 갱신하는 미들웨어를 작성한다.
5. 대화방 제목을 수정하는 `PATCH /conversations/{id}` API를 구현한다.
