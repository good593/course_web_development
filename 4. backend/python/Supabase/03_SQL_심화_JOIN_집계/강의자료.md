# 3교시: SQL 심화 — UPDATE, DELETE, JOIN, 집계, 페이지네이션

**소요시간:** 90분 (이론 30분 + 실습 60분)  
**사전 지식:** 2교시(Supabase 설정, SELECT·INSERT 기초)

---

## 학습 목표

- `UPDATE`와 `DELETE`를 안전하게 사용한다 (WHERE 없는 실수 방지)
- `INNER JOIN`으로 여러 테이블을 한 번에 조회한다
- `COUNT`, `GROUP BY`로 집계 쿼리를 작성한다
- `LIMIT`, `OFFSET`으로 페이지네이션을 구현한다
- 인덱스의 동작 원리와 필요성을 설명한다

## 1. UPDATE — 데이터 수정

```sql
-- 기본 UPDATE
UPDATE public.app_users
SET display_name = '김강사'
WHERE id = '사용자-UUID';

-- 여러 컬럼 동시 수정
UPDATE public.conversations
SET title = '수정된 제목', updated_at = NOW()
WHERE id = '대화방-UUID';
```

### ⚠️ WHERE 없이 UPDATE하면 전체가 수정됩니다!

```sql
-- ❌ 위험! 모든 사용자의 display_name이 '테스트'로 바뀜
UPDATE public.app_users SET display_name = '테스트';

-- ✅ 안전: WHERE로 특정 행만 수정
UPDATE public.app_users
SET display_name = '테스트'
WHERE id = '특정-사용자-UUID';
```

### UPDATE 후 변경된 값 확인

```sql
-- RETURNING으로 수정된 행 바로 확인
UPDATE public.app_users
SET display_name = '김강사'
WHERE id = '사용자-UUID'
RETURNING *;
```

### UPDATE 적용 전 SELECT로 먼저 확인하는 습관

```sql
-- 1단계: 먼저 바꿀 행이 맞는지 SELECT로 확인
SELECT * FROM public.app_users WHERE id = '사용자-UUID';

-- 2단계: 확인 후 UPDATE
UPDATE public.app_users SET display_name = '김강사' WHERE id = '사용자-UUID';
```

## 2. DELETE — 데이터 삭제

```sql
-- 특정 행 삭제
DELETE FROM public.conversations WHERE id = '대화방-UUID';

-- 조건으로 여러 행 삭제
DELETE FROM public.messages WHERE role = 'system';
```

### ⚠️ WHERE 없이 DELETE하면 테이블 전체가 비워집니다!

```sql
-- ❌ 절대 실수하면 안 됨! 모든 메시지 삭제
DELETE FROM public.messages;

-- ✅ 안전: WHERE로 특정 행만 삭제
DELETE FROM public.messages WHERE id = '메시지-UUID';
```

### CASCADE 삭제 확인

```sql
-- 대화방 삭제 시 그 대화방의 메시지도 자동 삭제됨
-- (schema.sql에 ON DELETE CASCADE가 설정되어 있으므로)

-- 삭제 전 메시지 수 확인
SELECT COUNT(*) FROM public.messages WHERE conversation_id = '대화방-UUID';

-- 대화방 삭제
DELETE FROM public.conversations WHERE id = '대화방-UUID';

-- 메시지 자동 삭제 확인 (빈 결과)
SELECT COUNT(*) FROM public.messages WHERE conversation_id = '대화방-UUID';
```

## 3. JOIN — 여러 테이블 연결

JOIN은 두 테이블을 공통 컬럼(보통 FK-PK)으로 연결해 한 번에 조회합니다.

### 왜 JOIN이 필요한가

```sql
-- 메시지만 조회하면 어느 대화인지, 누구의 것인지 모름
SELECT * FROM public.messages;
-- conversation_id: 'c1', role: 'user', content: '안녕'
-- → 어느 대화인지 알기 어려움
```

### INNER JOIN 기본 문법

```sql
SELECT
  테이블A.컬럼,
  테이블B.컬럼
FROM 테이블A
JOIN 테이블B ON 테이블B.컬럼 = 테이블A.컬럼;
```

### 메시지 + 대화방 JOIN

```sql
SELECT
  m.id        AS message_id,
  m.role,
  m.content,
  c.title     AS conversation_title,
  m.created_at
FROM public.messages m
JOIN public.conversations c ON c.id = m.conversation_id
ORDER BY m.created_at ASC;
```

테이블에 별칭(alias)을 붙이면 코드가 짧아집니다.
- `messages m` → `m.컬럼`으로 참조
- `conversations c` → `c.컬럼`으로 참조

### 3개 테이블 JOIN (메시지 + 대화 + 사용자)

```sql
SELECT
  u.username,
  u.display_name,
  c.title         AS conversation_title,
  m.role,
  m.content,
  m.created_at
FROM public.messages m
JOIN public.conversations c ON c.id = m.conversation_id
JOIN public.app_users    u ON u.id = c.user_id
ORDER BY m.created_at ASC;
```

이 쿼리 하나로 3개 테이블의 데이터가 합쳐진 결과를 얻습니다.

### JOIN 조건이 중요한 이유

```sql
-- ❌ ON 조건 없이 JOIN → 카테시안 곱 (모든 조합)
-- messages 10개 × conversations 5개 = 50개 행 (의미 없는 데이터)
SELECT * FROM messages, conversations;

-- ✅ FK로 올바르게 연결
SELECT * FROM messages m
JOIN conversations c ON c.id = m.conversation_id;
```

## 4. COUNT와 GROUP BY — 집계

### COUNT

```sql
-- 전체 메시지 수
SELECT COUNT(*) FROM public.messages;

-- role별 메시지 수
SELECT role, COUNT(*) AS 개수
FROM public.messages
GROUP BY role;

-- 결과 예시:
-- role      | 개수
-- user      | 15
-- assistant | 14
-- system    | 1
```

### GROUP BY 사용 규칙

```sql
-- ✅ GROUP BY에 없는 컬럼은 반드시 집계 함수로 감싸야 함
SELECT role, COUNT(*) FROM messages GROUP BY role;

-- ❌ 오류: content는 GROUP BY에 없고 집계도 아님
SELECT role, content, COUNT(*) FROM messages GROUP BY role;
```

### 사용자별 대화 수

```sql
SELECT
  u.username,
  COUNT(c.id) AS 대화수
FROM public.app_users u
LEFT JOIN public.conversations c ON c.user_id = u.id
GROUP BY u.id, u.username
ORDER BY 대화수 DESC;
```

### HAVING — 집계 결과에 조건 걸기

```sql
-- 메시지가 5개 이상인 대화방만 조회
SELECT
  conversation_id,
  COUNT(*) AS 메시지수
FROM public.messages
GROUP BY conversation_id
HAVING COUNT(*) >= 5
ORDER BY 메시지수 DESC;
```

> `WHERE`는 행을 집계하기 **전에** 필터링, `HAVING`은 집계 **후에** 필터링합니다.

## 5. LIMIT와 OFFSET — 페이지네이션

한 번에 모든 데이터를 가져오면 수천 건이 넘을 때 느려집니다.  
`LIMIT`와 `OFFSET`으로 페이지 단위로 나눠서 가져옵니다.

```sql
-- 최신 메시지 10개만
SELECT * FROM public.messages
ORDER BY created_at DESC
LIMIT 10;

-- 2페이지 (11번째 ~ 20번째)
SELECT * FROM public.messages
ORDER BY created_at DESC
LIMIT 10 OFFSET 10;

-- 3페이지 (21번째 ~ 30번째)
SELECT * FROM public.messages
ORDER BY created_at DESC
LIMIT 10 OFFSET 20;
```

**패턴:** `OFFSET = (페이지 번호 - 1) × LIMIT`

| 페이지 | LIMIT | OFFSET |
|--------|-------|--------|
| 1 | 10 | 0 |
| 2 | 10 | 10 |
| 3 | 10 | 20 |
| N | 10 | (N-1) × 10 |

### 주의: ORDER BY 없이 OFFSET 사용하면 결과가 불안정

```sql
-- ❌ 정렬 없이 OFFSET → 페이지마다 다른 결과 나올 수 있음
SELECT * FROM messages LIMIT 10 OFFSET 10;

-- ✅ 항상 ORDER BY와 함께 사용
SELECT * FROM messages ORDER BY created_at DESC LIMIT 10 OFFSET 10;
```

## 6. 서브쿼리 — 쿼리 안의 쿼리

```sql
-- 특정 사용자의 대화방 ID 목록을 먼저 구하고,
-- 그 대화방들의 메시지를 모두 가져오기
SELECT * FROM public.messages
WHERE conversation_id IN (
    SELECT id FROM public.conversations
    WHERE user_id = '사용자-UUID'
);
```

JOIN으로도 같은 결과를 낼 수 있지만, 서브쿼리는 직관적으로 읽히는 상황에서 유용합니다.

## 7. 인덱스의 동작 원리

### Full Table Scan vs B-Tree Lookup

```sql
-- 인덱스 없이: messages 전체를 순서대로 읽음
SELECT * FROM messages WHERE conversation_id = 'c1';
-- 10만 건이면 10만 번 비교
```

```
인덱스 있을 때 — B-Tree 구조
         c5
        /   \
      c2     c8
     /  \   /  \
   c1   c3 c6  c9

→ c1을 찾으려면 3번만 비교하면 됨
  (log₂(10만) ≈ 17번)
```

### 인덱스 생성 시점

```sql
-- 자주 WHERE/JOIN/ORDER BY에 쓰이는 컬럼에 생성
CREATE INDEX IF NOT EXISTS idx_conversations_user_id
  ON public.conversations(user_id);

-- 복합 인덱스: conversation_id로 필터 + created_at으로 정렬
CREATE INDEX IF NOT EXISTS idx_messages_conversation_id_created_at
  ON public.messages(conversation_id, created_at);
```

### 언제 인덱스를 만들어야 할까

```
✅ 인덱스가 도움 되는 경우:
  - WHERE conversation_id = 'xxx'     (FK 컬럼)
  - ORDER BY created_at DESC          (자주 정렬하는 컬럼)
  - JOIN ON c.id = m.conversation_id  (JOIN 조건 컬럼)

❌ 인덱스가 불필요한 경우:
  - 데이터가 100건 미만인 작은 테이블
  - 모든 행을 항상 가져오는 경우 (인덱스 검색 비용 > Full Scan)
  - UPDATE/INSERT가 매우 자주 일어나는 컬럼 (인덱스 업데이트 비용)
```

## 8. Supabase Table Editor 활용

SQL만으로는 직관적이지 않을 때 Table Editor를 사용합니다.

- **테이블 내용 보기**: 좌측 메뉴 → Table Editor → 테이블 선택
- **행 직접 추가**: `+ Insert row` 버튼
- **행 수정**: 셀 클릭 후 편집
- **행 삭제**: 행 선택 → Delete
- **필터/정렬**: 상단 바의 Filter, Sort 버튼

> **팁**: Table Editor는 소량 데이터 확인에 좋고, 복잡한 조건이나 JOIN은 SQL Editor에서 합니다.

## 흔한 실수와 해결법

| 실수 | 문제 | 해결 |
|------|------|------|
| `UPDATE` WHERE 없이 실행 | 모든 행이 수정됨 | 반드시 WHERE 절 포함 |
| `DELETE` WHERE 없이 실행 | 테이블이 비워짐 | 반드시 WHERE 절 포함 |
| JOIN ON 조건 빠뜨림 | 카테시안 곱 (행 수 폭발) | ON 절 반드시 포함 |
| GROUP BY 없이 집계 | 오류 발생 | SELECT에 집계 아닌 컬럼은 GROUP BY에 포함 |
| ORDER BY 없이 OFFSET | 페이지별 결과 일관성 없음 | 항상 ORDER BY와 함께 사용 |
| HAVING과 WHERE 혼동 | 원하는 결과 안 나옴 | 집계 전 필터 = WHERE, 집계 후 필터 = HAVING |

## 핵심 패턴 요약

| 작업 | SQL |
|------|-----|
| 행 수정 | `UPDATE 테이블 SET col=val WHERE id='...'` |
| 행 삭제 | `DELETE FROM 테이블 WHERE id='...'` |
| 두 테이블 JOIN | `JOIN 테이블B ON 테이블B.fk = 테이블A.pk` |
| 행 개수 집계 | `SELECT col, COUNT(*) FROM 테이블 GROUP BY col` |
| 집계 후 필터 | `HAVING COUNT(*) >= N` |
| 첫 N개 | `LIMIT N` |
| N번째부터 | `LIMIT N OFFSET M` |
